# 在 UEFI Shell 下用 Rust 写画图 App —— 技术可行性调研

调研时间：2026-09-27
目标：判断「Rust 编写、在 UEFI Shell 下运行的绘图应用」在技术上的可行性与推荐路线。

---

## 0. 结论速览

| 你问的问题 | 结论 | 关键证据 |
|---|---|---|
| 微软那套 Rust UEFI 是什么 | **Patina**（ODP 计划），纯 Rust 实现的 UEFI **固件**，不是 `microsoft/rust_uefi`（该仓库 404） | github.com/OpenDevicePartnership/patina，2025-10-07 UEFI Plugfest 公开 |
| QEMU 上跑 Rust UEFI 行不行 | **完全可行，且是官方推荐路径**，工具链一条命令 | Rust Tier-2 target `x86_64-unknown-uefi`；`uefi-run` / `cargo xtask run` |
| 有 Rust 的 Shell 吗 | **没有成熟的，也不需要** | UEFI Shell 本身就是普通 UEFI 应用，语言无关 |
| 现在的 Rust UEFI 能跑老 Shell 吗 | **能，直接跑** | Shell 用 `LoadImage()`/`StartImage()` 加载任意 PE/COFF `EFI_APPLICATION`；Patina 每个 PR 都在 QEMU 上启动到 EFI Shell |
| Rust 图形界面能搞吗 | **能**，GOP 底座成熟；四档方案按质量/成本取舍 | `uefi::proto::console::gop`、`embedded-graphics-gop`、`tiny-skia`、`rlvgl` |

**一句话**：技术路径畅通，无阻塞性风险。真正的工程难点不在「能不能跑」，而在「Shell 控制台与图形全屏接管如何切换」和「绘图性能/脏矩形刷屏」。

## 1. 先纠正一个前提：微软那套叫 Patina，不是 `rust_uefi`

你记忆里的「微软开源了一套 UEFI 的 Rust 实现」指向的是 **Patina**：

| 项 | 内容 |
|---|---|
| 仓库 | `github.com/OpenDevicePartnership/patina` |
| 归属 | Open Device Partnership（ODP），微软主导，2025-10-07 在 UEFI 2025 Developer Conference & Plugfest 上公开 |
| 定位 | **纯 Rust 的 UEFI 固件实现**，替换 DXE Core，明确表态「不是把 C code 包一层 Rust」 |
| 产品化 | 已部署在生产环境（虚拟机 + 物理机，从笔记本到服务器）；微软 SFI 报告称 Surface 用内存安全语言开发 UEFI 固件 |
| 组件 | `patina_dxe_core`、`patina_sdk`、`patina-edk2`、`patina-qemu`（Q35 / SBSA 两个参考虚拟平台）、`patina-mtrr`、`patina-paging`、`patina-readiness-tool`、`patina-fw-patcher` |
| 构建 | `cargo make build-x64` / `build-aarch64` / `build`；产物是 DXE Core 的 `.efi`，用标准 `x86_64-unknown-uefi` / `aarch64-unknown-uefi` target |
| 定位声明 | 原文：*"Patina's goal is to be the safest UEFI implementation available, not the most compatible"* |

### 注意两点

1. **`github.com/microsoft/rust_uefi` 不存在（404）**。容易混淆的邻居还有：
   - **Project Mu**（`microsoft/mu_*`）：2023 年起支持在 UEFI 代码库里混入 Rust 模块，`mu_tiano_platforms` 的 Q35 平台已含 DXE Rust 模块做 CI 演示；
   - **windows-drivers-rs**：Windows 驱动（WDF）的 Rust 框架，**不是** UEFI 应用框架；
   - **Rust 官方 UEFI target + `rust-osdev/uefi-rs`**：这才是写 UEFI **应用** 的主流生态（见第 2 节）。

2. **Patina 对你的画图 App 没有直接帮助，但有战略价值**。Patina 是固件层（它替代的是 OVMF/EDK2 的 DXE Core），它不提供 GUI 框架，你的 App 也不依赖它。它的价值在于：
   - 证明「Rust 写 UEFI」已被厂商级采用，不是玩具；
   - **它的 CI 每个 PR 都要在 AArch64 和 x64 QEMU 上引导到 EFI Shell** —— 这是「Rust 固件 + 传统 EDK2 Shell 共存」的最强实证。

## 2. QEMU 上跑 Rust UEFI：成熟路径

### 2.1 编译底座

Rust 官方提供三个 Tier-2 UEFI target：

```
x86_64-unknown-uefi
i686-unknown-uefi
aarch64-unknown-uefi
```

特性（决定了写 App 的约束）：

- 产物是 **PE32+**，subsystem = `EFI_APPLICATION`，入口 `efi_main`，用 LLD 链接；
- **必须静态链接**，不支持动态链接；
- panic strategy = abort；
- **默认禁用 MMX/SSE/FP 单元**（因为要能在固件初始化早期跑）；
- `no_std` 环境；`alloc` 可用（需自带 allocator）；`std` 支持「存在但极新且不完整」。

```bash
rustup target add x86_64-unknown-uefi
cargo build --target x86_64-unknown-uefi
# → target/x86_64-unknown-uefi/debug/xxx.efi
```

### 2.2 `uefi` crate（rust-osdev/uefi-rs）当前状态

- 稳定版可用（**MSRV 1.91**，跟上最近两个 stable），不需要 nightly（除非用 `unstable` feature）；
- 许可证：Apache-2.0 / MIT 双许可；
- 关键 feature（都在最新文档里确认过）：
  - `alloc` + `global_allocator`：官方「强烈建议」开启，直接用 UEFI pool 做全局分配器；
  - `logger` / `panic_handler`：开箱即用的日志与 panic 处理；
  - **`log-debugcon`**：日志同时写到 QEMU / Cloud Hypervisor 的 debugcon 设备 —— 无头调试利器；
  - **`qemu`**：panic 时走 `qemu-exit` 设备退出，**CI 友好**（能拿到确定退出码）；
  - `fs` 模块：近似 `std::fs` 的文件系统 API；`driver` 模块：UEFI 驱动模型高层封装。
- 生态配套：`uefi-raw`（裸绑定）、`uefi-macros`、官方 **UEFI application template**、**Rust UEFI Book**（含 QEMU 教程）。

### 2.3 运行到 QEMU 的三种方式

| 方式 | 命令 / 做法 | 说明 |
|---|---|---|
| `uefi-run` | `cargo install uefi-run` → `uefi-run ./app.efi` | QEMU 的薄封装，一行起 |
| uefi-rs 自带 xtask | `cargo xtask run --headless` | 官方 CI 同款，可指定 `--ovmf-code` / `--ovmf-vars` |
| 手工 OVMF + vvfat | `OVMF_CODE.fd` + `OVMF_VARS.fd` + `-drive format=raw,file=fat:rw:esp` | 最可控，可挂 monitor 抓帧 |

## 3. Shell 问题：不需要 Rust Shell，老 Shell 直接跑 Rust `.efi`

这是本次调研最干净的结论，值得展开说清楚。

### 3.1 原理：Shell 是「应用加载器」，与语言无关

UEFI Shell 自己就是一个普通的 UEFI 应用（`Shell.efi`），它执行一条命令时做的是：

```c
// EDK2: ShellPkg/Application/Shell/ShellProtocol.c
InternalShellExecuteDevicePath(...)
    Status = gBS->LoadImage(FALSE, *ParentImageHandle, DevicePath, NULL, 0, &NewHandle);
    ...
    gBS->StartImage(NewHandle, ...);
```

`LoadImage` 只认两件事：**PE/COFF 格式** 和 **subsystem = `EFI_APPLICATION`**。Rust 编译出的 `.efi` 恰好就是这个（`x86_64-unknown-uefi` target 默认设置）。**Shell 完全不知道也不关心这个镜像用什么语言写的。**

所以：

```
Shell> map -r
Shell> fs0:
Shell> cd efi\tools
Shell> MyPaint.efi        ← Rust 编译出来的，Shell 照跑不误
```

### 3.2 三个实证

1. **Patina 的 CI**：每个 PR 都在 AArch64 / x64 QEMU 上「**boots to the EFI Shell**」后才允许合并 —— Rust 固件 + 传统 EDK2 Shell 已经在生产级流程里共存。
2. **uefi-rs 专门为「运行在 Shell 下的 App」做了封装**（最新版确认）：
   - `uefi::proto::shell` —— `EFI_SHELL_PROTOCOL` **v2.2** 的高层封装（`Shell`、`Vars`、`ShellVarProvider`），可读写 Shell 环境变量（`get_env`/`set_env`/`get_map`）；
   - `uefi::proto::shell_params` —— **`ShellParams` 协议**，拿 `argc` / `argv`，即命令行参数。这说明 uefi-rs 在设计上就把「被 Shell 启动的命令行程序」当一等公民。
3. **Rust 官方平台支持文档**直接把「复制 .efi 到 ESP，通过固件启动菜单或 Shell 执行」写成标准测试流程。

### 3.3 Shell 从哪里来（三选一，都不需要编译 Rust）

| 来源 | 做法 |
|---|---|
| 本工作区现成 | 直接用 `D:\Work\Code\GopApp\Shell.efi`，或把它改名 `bootx64.efi` 放到 FAT 目录 `\EFI\BOOT\` |
| 预编译发行版 | `pbatard/UEFI-Shell`（GitHub Releases）：多架构 `Shellx64.efi` / 可引导 ISO；构建过程可审计（GitHub Actions 公开日志 + SHA 校验）。**注意：外部 Shell 无法通过 Secure Boot 签名，真机跑必须关 SB** |
| 自己编 EDK2 | `build -a X64 -p ShellPkg/ShellPkg.dsc -t GCC5/VS2019` → `Build/Shell/DEBUG_*/X64/Shell.efi` |

### 3.4 那几个「Rust 壳」的存在意义（结论：不用碰）

- 没有成熟的「Rust 重写 Shell」项目。有零散的自研封装（例如某些 hypervisor 项目里用 `ShellInterface` / `EFI_SHELL_PARAMETERS_PROTOCOL` 取 argv 的百来行代码），属于工程量极小的适配层，uefi-rs 已经内置。
- 如果你想要的是「用 Rust 写 Shell 内建命令」（像 `dir`/`edit` 那样），那本质是给 EDK2 Shell 写 App，仍然走 `ShellParams` + `Shell` 协议这条路，而不是重写 Shell。

### 3.5 两条运行路径对比

| 路径 | 优点 | 代价 |
|---|---|---|
| **EDK2 Shell + 你的 `.efi`**（推荐） | 零额外基础设施；命令历史/脚本/`fs0:` 导航白送；本工作区已有 Shell.efi + OVMF | 进入 App 后需自己接管屏幕（见第 5 节） |
| 直接作 `bootx64.efi` 被固件 BDS 启动 | 最贴近真实设备体验 | 没有 Shell 环境，只能用 `ShellParams` 之外的启动参数（如 UEFI 启动项 `load options`） |

**建议：走第一条。** 在 Shell 里 `MyPaint.efi --size 1280x800` 这种体验，正好是 `ShellParams` 的用武之地。

## 4. 图形：能搞，四档方案

### 4.1 底座：GOP（`EFI_GRAPHICS_OUTPUT_PROTOCOL`）

这是所有方案的公共根基，uefi-rs 封装为 `uefi::proto::console::gop::GraphicsOutput`：

```rust
let gop_handle = boot::get_handle_for_protocol::<GraphicsOutput>()?;
let mut gop = boot::open_protocol_exclusive::<GraphicsOutput>(gop_handle)?;

let info = gop.current_mode_info();
let (width, height) = info.resolution();   // 分辨率
let stride = info.stride();                // ← 扫描线像素数，≠ width！
let fmt = info.pixel_format();             // Rgb/Bgr/BltOnly

// 方式 A：直接写显存（快，但要自己管 stride/像素格式/边界）
let mut fb = gop.frame_buffer();
unsafe { fb.write_value::<u32>(index, 0x00FF0000) }

// 方式 B：Blt 推送（EmulatorPkg 下必须用这个）
gop.blt(BltOp::BufferToVideo { buffer, src, dest, dims })?;
```

**必须记住的三个坑**：

1. **stride ≠ width**。`pixels_per_scan_line` 是显存里每行实际像素数（通常有 padding）。行偏移必须用 `y * stride + x`，用 `y * width + x` 会画出斜的斜着拧的图。
2. **像素格式不一定是 RGB**。UEFI 历史上是 BGRx，现代有 RGBx / BltOnly。写死颜色值会导致红蓝互换。
3. **EmulatorPkg/WinHost 的 GOP 可能没设 `FrameBufferBase`** → 直接访问 `frame_buffer()` 会挂。**在 Emulator 路径下必须走 `Blt()`**。这个问题在本工作区已被记录过。

### 4.2 四档图形方案对比

| 档 | 方案 | 依赖 / 版本 | 成熟度 | 适合 | 风险 |
|---|---|---|---|---|---|
| **A** | **手写光栅器 + GOP** | 只需 `uefi` | 由你自己保证 | 画笔/示波器/矢量仪表这类**图元有限、要极致可控**的场景。最快、体积最小、无 SIMD 依赖 | 抗锯齿、曲线、渐变、文字排版全要自己写 |
| **B** | **`embedded-graphics` + `embedded-graphics-gop`** ⭐ | `embedded-graphics-gop` v0.4.1（MPL-2.0，MSRV 1.85.1，548 SLoC） | 专为 GOP 写的 `DrawTarget`，提供 **Blt 后端** 和 **framebuffer 后端**，`no_std`，可选 `no-alloc` | **本项目推荐起点**：线/圆/矩形/多边形/位图直接可用；文字配 `embedded-text` 或位图字体 | `embedded-graphics` 是嵌入式定位，**无抗锯齿、无 alpha 混合**，做「画图工具」够用，做「现代 UI」吃力 |
| **C** | **`tiny-skia`** | 纯 Rust 2D 库，`no_std + alloc` | 成熟（Skia 子集：路径、抗锯齿、渐变、混合模式） | 要做**真正的画图软件体验**：手绘平滑笔迹、抗锯齿曲线、图层混合 | 体积大；**默认开启 SIMD（SSE/AVX）而 UEFI target 默认禁 MMX/SSE** → 必须关 simd feature 或显式加 `target-feature`；需要 `libm` |
| **D** | **`rlvgl`** | v0.2.5（2026-07-14），MIT，107K SLoC | **Rust 重写版 LVGL**，有**真实 UEFI target**：`rlvgl-uefi-disco`，`make test-uefi-disco` 会「builds it headless under QEMU (EDK2 firmware) + pl011 UART」 | 想要**完整 widget 体系 + UI 状态机 + 动效** | 很年轻、偏 AArch64/QEMU + STM32H747I-DISCO 单板、社区小（33 下载/月），**押注风险高**，建议只做技术观察 |
| **E** | `lvgl` crate（`lv_binding_rust` / `lvgl-sys`） | 绑定 C 版 LVGL，**仍钉在 8.3.5**（lvgl-sys 0.6.2，2023-04） | 需要 `clang`/`bindgen` + `DEP_LV_CONFIG_PATH`，构建走 Cargo 编 C，还得混进 EDK2 构建 | 想把现有 LVGL 资产搬过来 | **不是纯 Rust 路子**；版本落后于你在用的 9.2.2；Cargo × EDK2 双构建体系耦合，调试成本高 |

**推荐组合**：`uefi` + `embedded-graphics` + `embedded-graphics-gop` 打底 → 笔迹平滑/抗锯齿需求出现时，**只替换渲染后端换 `tiny-skia`**（上层几何数据结构不用动）。

### 4.3 字体与文字

| 需求 | 方案 |
|---|---|
| 少量固定文案（工具栏标签） | 位图字体（`embedded-graphics` 的 mono font / 自己一张 8×16 表）——零依赖、最快 |
| 任意字符串排版 | `embedded-text`（embedded-graphics 生态的排版层） |
| TTF/OTF 矢量字体、任意字号 | `fontdue`（`no_std + alloc`，纯 Rust 光栅化）、`ab_glyph`、`swash`；配合 `libm` |

### 4.4 输入

| 设备 | 协议 | uefi-rs |
|---|---|---|
| 键盘（按键） | `EFI_SIMPLE_TEXT_INPUT_PROTOCOL` | `proto::console::text::Input`（`read_key` / `check_key`），键值 `Key::{Printable, Special}`，`Special` 含 Up/Down/Left/Right/Esc 等扫描码 |
| 键盘（带修饰键/Ex 事件） | `EFI_SIMPLE_TEXT_INPUT_EX_PROTOCOL` | `proto::console::text` |
| 鼠标/触摸 | `EFI_SIMPLE_POINTER_PROTOCOL` | `proto::console::pointer::Pointer`（`read_state` / `wait_for_input`） |

事件循环用 `boot::wait_for_event(&[con_in.wait_for_key()])` 阻塞等待，或 `check_key()` 轮询 —— 后者更适合需要持续动画/重绘的场景。

## 5. 关键坑与硬约束（写代码前必读）

| # | 约束 | 影响 | 应对 |
|---|---|---|---|
| 1 | **控制台与图形互斥** | 一旦 `open_protocol_exclusive::<GraphicsOutput>()` 并 `set_mode()`，`SimpleTextOutput` 的输出就乱了（但 `stdin` 仍可用） | App 采用「**全屏接管**」模型：进入时保存并切换视频模式，退出时 `drop(gop)` 恢复控制台模式，Shell 提示符正常回来。这是 App **从** Shell **被启动**，不是 Shell 内建命令 |
| 2 | **单 CPU、单栈、协作式、禁止中断** | 除定时器中断外不允许用中断；驱动必须轮询；不能有真正的多线程 | 单线程主循环 + `check_key()` 轮询；需要"后台"就自己写状态机分帧 |
| 3 | **stride / 像素格式** | 见 4.1，画错不会报错，只会画面歪 | 封装 `Canvas { ptr, stride, w, h, fmt }`，所有绘制只走它 |
| 4 | **UEFI target 默认禁 MMX/SSE** | 任何依赖 SIMD 的 crate 可能编不过或跑飞（`tiny-skia` 默认开 `simd`） | 关掉 crate 的 simd feature；或 `RUSTFLAGS="-C target-feature=+sse2"`（需确认固件已初始化 FPU） |
| 5 | **no_std 无浮点数学** | `sin`/`sqrt`/`atan2`（画笔的圆平滑、旋转）不可用 | 加 `libm` crate |
| 6 | **分配器 = UEFI pool，不回收 page** | 大量 `Vec` 反复分配会碎片化，固件内存不像 OS 有 swap | 用 `global_allocator` feature；**全屏后备缓冲在启动时一次性分配**，绘图期零分配 |
| 7 | **QEMU 无键盘自动重复** | 「按住方向键连续移动」在 QEMU 里失效 | 自己实现 key-repeat 状态机（按下计时后自动重复），顺带解决真机手感；自动化测试用 `sendkey` 连点 |
| 8 | **性能：全屏 Blt 是软件拷贝** | 1920×1080×4B ≈ 8MB/帧，QEMU 下每帧全屏推送很慢 | 双缓冲 + **脏矩形**，只 Blt 变化的区域；或纯 framebuffer 直写 + 只在需要时同步 |
| 9 | **Secure Boot / 签名** | 真机跑未签名 `.efi` 会被拒（外部 Shell 本身也无法通过 SB 签名） | 开发期用 QEMU/OVMF（无此限制）；上真机需关 SB 或自签名 + 导入 db |
| 10 | **Shell 退出后的屏幕残留** | App 退出后 Shell 重印提示符，画面内容丢失 | 若要"返回后仍有画面"，需在进入前保存控制台文本模式内容并恢复；否则接受 Shell 重绘 |

## 6. 建议路线（分阶段，每阶段可独立验证）

### Phase 0 — 工具链就位（唯一缺失项）
```bash
# 安装 rustup（Windows: rustup-init.exe），然后：
rustup target add x86_64-unknown-uefi
cargo install uefi-run
```
验证：`cargo new hello-uefi` + 官方模板 → `uefi-run ./hello.efi` 在 QEMU 里看到输出。

### Phase 1 — 验证「Rust App 在传统 Shell 下」
复用本工作区现有资产，不新建基础设施：
1. 把 Rust 编出的 `.efi` 放进一个 FAT 目录；
2. `qemu-system-x86_64 -drive if=pflash,...,file=D:/Work/Code/GopApp/OVMF.fd -drive format=raw,file=fat:rw:esp`；
3. 或者干脆用 EmulatorPkg：`WinHost.exe` 启动后 `fs0:` → 把 `.efi` 拷进 WinHost 所在目录 → `MyApp.efi`（EmulatorPkg 的 `fs0:` 映射宿主工作目录）。

**这一步是本项目最大的不确定性来源，必须先做掉。** 验证成功后，后面全是纯 Rust 实现问题。

### Phase 2 — 最小绘图内核
`uefi` + GOP：双缓冲后备缓冲、`Canvas` 抽象（含 stride/像素格式）、`putpixel`/`line`/`rect`/`fill`、脏矩形 Blt 刷屏、`check_key` 轮询退出。产物：能在 Shell 下跑起来、用键盘画线的黑白 App。

### Phase 3 — 引入 2D 图元与文字
接入 `embedded-graphics` + `embedded-graphics-gop`，加工具栏、调色板、位图字体标签；实现画笔/橡皮/直线/矩形/填充/撤销栈。

### Phase 4 —（按需）画质升级
若需要抗锯齿手绘笔迹/曲线平滑：换 `tiny-skia` 后端（注意 SIMD 约束）。若要做完整 UI 框架：单独评估 `rlvgl`。

## 7. 验证清单（每完成一步都应留证据）

- [ ] 串口/debugcon 日志里出现一致的 `APP_VERSION=`（版本化构建，避免跑到旧 `.efi`）
- [ ] QEMU monitor `screendump` 抓到的 PNG 里能看到目标画面
- [ ] `.efi` 的 subsystem 是 `EFI_APPLICATION`（`dumpbin /headers` 或 `objdump -p`）
- [ ] 在 Shell 下能通过 `ShellParams` 拿到命令行参数
- [ ] 退出 App 后 Shell 提示符可正常交互（验证控制台模式已恢复）
- [ ] 全屏重绘耗时在可接受范围（验证脏矩形生效）
